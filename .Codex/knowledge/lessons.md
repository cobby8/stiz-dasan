## 2026-10-22 모바일 이동은 주소 진입과 실제 링크 순회를 모두 검사한다
- URL 직접 로딩이 성공해도 메뉴 클릭/상세 복귀/가입 방법 전환이 정상이라는 뜻은 아니다. 외부 referrer 없는 첫 진입부터 Next Link로 이동한 세션에서 헤더 뒤로와 브라우저 뒤로를 비교한다.
- 입력 검증은 새 신청뿐 아니라 기존 자료를 불러온 다음·사용자가 정정한 다음·제출 직전에 확인한다. 오류 시 값이 남는 것과 오류 안내가 화면에 보이는 것도 별개의 검증 항목이다.

## 2026-10-22 공개 UI 검증은 표시 의미와 최초 실행을 분리한다
- 화면 넘침이 없어도 종료된 특강의 잔여석·신청 문구는 틀릴 수 있다. 목록·상세·직접 신청을 같은 현재 시각과 모집/수업 상태로 대조한다. 기간 경계뿐 아니라 만석·수업 없음·잘못된 일정도 포함한다.
- 이미 열린 브라우저의 재시작 성공은 첫 실행 성공을 보장하지 않는다. 가이드는 새 브라우저·일반/큰 글씨·빠른 확인 클릭으로 검사하며, 간헐 실패를 한 번의 성공으로 덮지 않는다. 명시적 폭·불필요한 전환 효과 제거처럼 최초 치수와 상태가 확정되는 방식으로 고친다.

## 2026-10-20 공개 홈페이지 변경 철회
- 기존 홈페이지의 인상과 구성에 대한 선호를 충분히 맞추지 못한 채 공통 테마와 구성 축소를 넓게 적용해 사용자가 거절했다. 기존 디자인 유지가 현재 결정이며 새로운 리디자인은 별도 요청 전 추진하지 않는다.

## 2026-07-11: 관리자 대시보드는 핵심 요약과 무거운 통계를 분리한다
- 현상: 운영 탭에서 `/admin` 첫 진입이 약 25초까지 늘어났고, `/admin/students`는 DOM 3천 개 이상과 버튼 700개 이상을 한 번에 렌더링했다.
- 원인: 첫 화면에 꼭 필요한 요약, 월별 차트, 최근 학생/요청 목록, 긴 원생 테이블을 한 번에 준비하고 그리면 DB 쿼리보다 화면 준비와 네트워크 왕복이 더 크게 느껴진다.
- 해결: 대시보드는 핵심 요약 payload를 먼저 보여주고 상세 통계는 백그라운드에서 채우며, 원생 목록은 최초 50명만 그리고 더 보기로 점진 렌더링한다.
- 예방: 관리자 페이지는 “첫눈에 볼 숫자”와 “클릭하거나 스크롤해야 볼 정보”를 분리한다. 긴 목록은 가상화 또는 페이지 단위 렌더링을 기본값으로 둔다.

## 2026-07-11: 관리자 주 본문은 캐시 서버 payload가 client fetch보다 낫다
- 현상: `/admin/programs`, `/admin/schedule`은 관리자 셸이 1초대에 먼저 보였지만, 실제 본문은 클라이언트 API를 기다리느라 약 5초 뒤 표시됐다.
- 원인: 서버 렌더를 줄이려고 본문 데이터를 브라우저 fetch로 미루면, 사용자는 빈 껍데기를 먼저 보고 실제 업무 화면을 다시 기다리게 된다.
- 해결: 선생님이 진입 즉시 봐야 하는 주 본문 데이터는 `unstable_cache`로 짧게 캐시한 서버 payload를 페이지 첫 렌더링에 주입한다.
- 예방: “자주 쓰는 목록/시간표/CRM”은 첫 화면에 싣고, “수강생 선택 목록/설정/모달 내부 보조 데이터”처럼 필요할 때만 보는 데이터만 뒤로 미룬다.

## 2026-07-06: 문서보다 코드가 더 최신일 수 있다
- 개발 기록 문서는 2026-03-20 기준 내용이 많지만, 실제 최근 커밋은 리치 에디터, 다크모드, 신청 폼, 공지 개선까지 더 진행되어 있었다.
- 앞으로는 문서를 먼저 읽되, 실제 라우트/메뉴/스키마/최근 커밋으로 반드시 대조한다.

## 2026-07-06: 프로젝트 이름만 보고 쇼핑몰로 단정하지 않는다
- 사용자가 “쇼핑몰”이라고 표현해도 실제 저장소는 학원 운영 플랫폼일 수 있다.
- 기능 구조를 먼저 확인한 뒤 현재 프로젝트의 정확한 성격을 맞춘다.

## 2026-10-19: 생산 초기 화면 오류는 개발 모드 검사로 종결하지 않는다
- 동일 화면도 개발18회 오류0과 생산90회 오류12가 달랐다. 실제 오류 순간의 DOM 위치와 공식 패키지 코드를 비교하니 화면 변경이 아니라 프레임워크 재시도 결함이었다. 경고 숨김이나 관련 없는 버튼 변경 대신 정식 최소 수정 버전으로 같은 조건을 대조한다.
- 실제 운영 로그인, 합성 인증을 쓰는 최신 소스, PC 화면 폭, 실물 기기의 페이지 픽셀과 물리 회전은 서로 다른 증거다. 하나가 통과했다고 다른 층을 완료로 올리지 않는다.

## 2026-10-20: 실기기 시험 서버 소유와 완료 신호
- 작업자에게 실행 세션을 전달받았더라도 완료 파일만으로 서버가 살아 있다고 판단하면 안 된다. 연결 전 HTTP와 실제 포트를 다시 확인하고 PM이 직접 실행을 소유한다.
- 시험 실행이 끊겼을 때 운영 환경을 끌어오지 않는다. 검증된 컴파일 결과의 해시를 대조한 재사용과 새 격리DB 복구를 구분하고, 병렬 작업 중 새로 바뀐 파일은 별도 최종 빌드에서 검사한다.

- 재부팅하면 실행기 세션·임시 서버가 사라진다. 저장된 결과와 실제 LISTEN 상태를 구분하고, 시험 자료만 복구한다. 준비 로그가 늦다는 이유만으로 실행 중인 자기 DB를 중단하지 않는다. 자동 승인 검토의 차단은 다른 도구로 우회하지 않는다.
- 2026-10-20: 역할별 경계 검사가 끝나도 전체320px 캡처·단어 Range·독립 QA가 끝나기 전에는 생산 빌드를 시작하지 않는다. 최종이라고 통보한 뒤 새 줄바꿈 결함이 나와 빌드를 반복 중단하는 낭비를 줄인다. 전후 비교는 원본 테마·글꼴·여백과 고정 커밋을 사용하며, 원본과 다른 예비 스타일 수치를 실제 개선량으로 인용하지 않는다.

## 2026-10-20: 전체 검사와 오래된 검증 도구의 경계
- 과거 문자열 검사를 통과하려고 화면에 개발 용어를 남기지 않는다. 실제 기능을 확인한 뒤 검사의 업무 의미를 유지한다. 예를 들어 별도 승인 조건은 검증하되 HELD라는 화면 표기를 강제하지 않는다.
- 컴파일·타입 검사·정적 이미지 생성·API/DB·브라우저 검증은 서로 다른 증거다. 복사한 소스·합성 인증 제공자·의존성 버전을 구분해 기록하고 해시로 대조한다. 후보 복사본 성공을 원본 빌드 성공으로 대신하지 않는다.

## 2026-10-20: 합성 성공과 실제 운영 근거 구분
- 합성 일정으로 계산이 맞더라도 운영 일정의 공급 경로가 빠지면 실제 사용은 불가능하다. 실제 자료 읽기 전용 화면까지 확인하고, 누락된 근거는 임의 생성 대신 보류해야 한다.
- 금액 수정뿐 아니라 원기간·출석·보강 예약/사용·취소·구형 청구 입구를 함께 검증해야 중복 보상을 막을 수 있다. 시험 성공 건수를 중복 합산하지 않는다.
## 2026-10-22 공개 자료 미리보기의 정합성
- 실제 사진·반·숫자가 맞아도 소개 문구·정책 문단을 재구성하면 원문과 같은 자료라고 보고할 수 없다. 원문 위치·본문 해시·줄 수·조항 수와 실제 렌더를 함께 대조해야 한다.
- UI 검사에서 정책의 아이콘 이름·영문 제목이 본문에 섞이는지, 같은 소개가 시설로 반복되는지 별도로 확인한다. 잘못 만든 검증 자료를 제품의 운영 내용 오류로 오해해 정책이나 API를 불필요하게 수정하지 않는다.
- DOM 원문 일치와 화면 넘침 없음만으로 충분하지 않다. 실제 스크린샷의 본문 가시성과 글줄 폭을 확인해 투명한 긴 래퍼·Card 중첩 패딩을 배포 전 잡는다.
## 2026-10-25 배포 성공과 실제 스타일 검증

- 서버가 이미 아는 공개 화면 여부를 주소 초기화에만 맡기면 스타일이 누락될 수 있다. 알려진 페이지의 명시값을 사용하되 기존 업무·설치 별칭의 범위를 무심코 넓히지 않는다.


## 2026-10-27 가족 연결의 전체 경계 검증
- 자녀 목록에 두 번째 가족이 보이는 것만으로 기능이 완성되지 않는다. 목록·상세·신청·사진·퇴회·승인함과 대표 결제 소유권을 함께 확인해야 한다.
- 원장이 아닌 기존 부모의 승인 경로에는 레거시 로그인까지 포함한 실제 계정 증거를 재사용하되, 전화번호만으로 로그인 계정을 합치거나 주 역할을 교체하지 않는다.
