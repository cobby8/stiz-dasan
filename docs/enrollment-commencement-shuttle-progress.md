# 수강 개시일·휴원 복귀일·셔틀 진행 상태

## 승인 범위와 운영 보류

2026-11-03 사용자 승인으로 로컬 코드·격리 검증만 진행한다. 운영 DB 구조/자료 변경, 실제 배차 저장, 문자·알림·청구, 푸시·배포는 실행하지 않는다. 기존 업무 화면의 스포츠 스타일과 메뉴는 유지한다.

## 날짜 기준

- 새 수강신청은 복수 월 선택 대신 수강 개시일 한 개를 받는다. `requestedStartOn`은 시간대 없는 달력 날짜다.
- 관리자가 배정 반과 개시일을 확인하면 신청 날짜와 반별 `Enrollment.startsOn`에 같은 날짜를 기록한다.
- 과거 `enrollmentMonths`는 삭제하거나 월의 첫날로 변환하지 않는다. 날짜 미확정은 목록·상세 모두 `개시일 확인 필요`, 상세에는 기존 월을 보존한다.
- 수강 상태 원본은 유지하고, 미래 개시일의 ACTIVE 수강은 화면에서 `수강 예정`으로 표시한다. 현재 출석 명단에는 해당 수업 날짜가 개시일 이상일 때만 포함한다.
- 개시일 이전 출결 저장도 서버에서 차단한다. 조회 화면에서만 숨기는 방식은 사용하지 않는다.
- 이미 ACTIVE인 동일 반에 대한 신청 승인은 첫 쓰기 전에 차단한다. 기존 수강 기간을 덮어쓰거나 신청 표시 날짜만 바꾸지 않는다.
- 기간 중 개시의 청구액은 임의로 확정하지 않고 검토 대상으로 남긴다. 개시 이전 기간의 청구 후보는 제외한다.
- 기존 nullable 개시일은 기존 동작을 보존한다. 일괄 과거 날짜 보정은 하지 않는다.

## 휴원 복귀 예정일

- 기존 `resumeOn` 저장 경로를 재사용한다. 날짜를 모르면 미정으로 제출할 수 있고, 선택한 날짜는 지울 수 있다.
- 휴원 시작일보다 뒤의 유효한 날짜만 허용한다. 신청 후 학부모 내역과 관리자 PC·모바일·상세에서 같은 값 또는 `복귀일 미정`을 표시한다.
- 복귀 예정일은 자동 복귀 실행 지시가 아니다. 이번 작업에서는 실제 휴원·복귀를 실행하지 않는다.

## 셔틀 상태

- 신청 접수, 위치 확인, 명단 반영, 배차 확정, 안내 발송과 최종 전달은 서로 다른 단계다.
- 안정적인 학생 ID, 적용 월, 배정 반의 요일, 등·하원 방향을 함께 대조한다. 이름만 같은 기록은 완료 근거로 쓰지 않는다.
- 명단만 있거나 과거 저장 노선에만 남은 학생은 배차 확정이 아니다. 명단·위치·시간·차량·기사 등 현재 자료와 저장 증거가 일치해야 한다.
- 월·수 등하원처럼 네 항목이면 `2/4 확정`으로 부분 상태를 보존한다. 한 항목 성공으로 전체를 완료시키지 않는다.
- 미래 개시일 신청은 개시 월에 맞는 명단을 조회한다. 과거 또는 다른 월의 배차를 완료 근거로 쓰지 않는다.
- 문자 공급자 접수는 `전달 미확인`이다. 현재 노선·수신자·문안과 연결된 최종 전달 성공만 `안내 완료`로 표시한다.
- 명단이 그대로라도 시각·차량·기사가 바뀌면 재안내가 필요하다. 기존 인증된 재대조 실행 경로를 재사용하며 새 예약 작업은 만들지 않는다.
- 조회 실패는 `확인 불가`로 표시한다. 미배정 또는 완료로 바꾸지 않는다.

## 운영 적용 전 필요한 절차

1. 코드 검증 결과와 마이그레이션을 검토한다.
2. 별도 운영 DB 승인 후 날짜 컬럼 두 개를 추가한다. 배포 과정에서 자동 ALTER하지 않는다.
3. 읽기 전용 사전 검사로 컬럼과 DATE 형식을 확인한다. 준비되지 않으면 운영 빌드를 차단한다.
4. 별도 배포 승인 후 운영 화면을 재검증한다.
5. 배차와 안내는 대상·시각·수신자를 확인받은 뒤 별도로 실행한다.
