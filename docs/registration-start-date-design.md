# 확정 수강 시작일 G3b 설계안

작성: 2026-09-09. 설계만 작성했으며 스키마·승인·이벤트 코드를 변경하지 않았다.

## 해결할 문제

현재 `EnrollmentApplication.enrollmentMonths`는 희망 신청월 문자열이다. `buildEnrollmentOperationsEvent`의 effectiveDate는 changedAt의 한국 날짜이며, 승인 처리일을 실제 수강 시작일로 사용할 수 없다. 기존 ACTIVE 수강은 승인 시 새 이벤트를 만들지 않는다. 따라서 G3a 조회 화면은 원장 출처만 연결하고 외부 등록 확인필요를 유지한다.

## 저장 단위 제안

- 여러 반의 시작일이 다를 수 있어 신청별 공통 날짜 하나 대신 신청·학생·반 단위 확정 기록을 둔다.
- 새 `EnrollmentStartConfirmation` 모델 후보: id, applicationId, studentId, classId, enrollmentId, startDate(date), confirmedByUserId, confirmedAt, basis, version, invalidatedAt. 신청·반별 활성 기록은 하나로 제한한다.
- 변경 이력은 별도 불변 revision 기록으로 보존한다. 기존 신청과 기존 수강에는 값을 자동 채우지 않는다. 학생 ID나 배정 반이 달라지면 기존 확정 기록을 그대로 재사용하지 않는다.
- 신규 승인 시 관리자에게 반별 날짜·근거를 명시 입력받는다. 학생·반·날짜·근거·버전을 같은 거래에 저장하고 감사 실패 시 승인을 포함해 되돌린다.
- 이미 ACTIVE인 수강의 원 시작일을 덮어쓰지 않는다. 기존 신청의 확인은 별도 검토·기록 동작으로 다루며 과거 승인 시각이나 신청월로 역산하지 않는다.

## 승인 화면·서버·이벤트 경계

1. `src/app/admin/apply/ApplyAdminModals.tsx`: classIds 선택을 반별 시작일/근거 입력과 함께 표시. 결정 전 학생·반·일자 미리보기 제공.
2. `src/app/actions/admin.ts`의 approveEnrollApplication: ID 집합·실제 날짜·최신 상태·담당자 권한을 서버에서 다시 검사. 부분 입력·반 누락·중복 반·이전 화면 버전은 거부한다.
3. `prisma/schema.prisma`와 신규 migration: 새 기록과 감사 구조만 작성. 운영 적용은 대상 구조와 기존 자료 불변을 확인한 별도 승인 대상이다.
4. 승인 결과 재조회용 타입·조회 매핑에 확정 기록을 추가한다. 단순 브라우저 입력값을 완료 증거로 취급하지 않는다.
5. `src/lib/operations-events/admin-hooks.ts`: 일반 상태변경 effectiveDate의 의미는 유지한다. 승인 경로 전용 확정 기록 ID/version과 startDate를 이벤트에 연결하는 방식부터 검토한다. source 날짜를 수강 적용일로 일괄 치환하지 않는다.

## 먼저 정해야 할 정책

- 미래 시작일을 기록만 할지, 미래일까지 현재 수강 ACTIVE 전환도 미룰지 결정이 필요하다. 현재 승인은 즉시 ACTIVE이므로 두 동작을 같은 것으로 간주할 수 없다. 예약 활성화는 별도 설계가 필요하다.
- 입력 가능한 과거/미래 기간, 날짜 정정 권한과 근거, 기존 ACTIVE/복귀 신청의 확정 방식은 운영 기준 합의가 필요하다.
- 시작일 기록만으로 청구·일할계산·시트·Rallyz 쓰기를 실행하지 않는다. 그 연결은 각각의 승인 범위를 가진 후속 그룹이다.

## 외부 등록 VERIFIED에 필요한 증거

- 동일 신청·학생·전체 배정 반의 확정 시작일 기록이 존재하고 유효해야 한다.
- 각 반의 고유 명령·수강 ID, WEBSITE/CLASS_ADD 출처, 확정 날짜·월, 무효화되지 않은 기록 버전이 정확히 맞아야 한다.
- 해당 타깃의 단일 SUCCEEDED와 유효 verifiedAt을 요구한다. 명령 생성 전·미래 시각, 중복·충돌·후속 변경을 배제한다. 다른 타깃 실패는 별도 상태로 남긴다.
- 자료 없음은 확인필요다. 청구·안내·초대·유니폼·담당자·셔틀은 별도의 직접 연결 증거를 요구한다.

## 검증과 출시 조건

다반별 다른 날짜, 누락/중복 입력, 미래 시작, 이미 ACTIVE, 복귀, 권한 실패, 두 관리자 경쟁, 감사 실패 롤백, 확정 뒤 반 변경/날짜 정정, 원장 재조회 시점 역전과 무효화를 검사한다. 격리 실제 DB 및 브라우저 검증 후 운영 적용·활성화 여부를 별도로 결정한다. G3a의 순수 함수 테스트를 실제 DB 검증으로 주장하지 않는다.
