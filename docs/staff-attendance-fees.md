# 출석 명단의 당월 금액·납부 상태

2026-10-19 · 로컬 검증 기록 · 운영 반영·배포 없음

## 변경 목적과 그룹

수업 중 학생이 결제하려고 할 때 선생님이 출석 명단에서 금액과 납부 상태를 바로 확인하고, 해당 학생의 실제 청구 창으로 이동하도록 개선했다.

| 그룹 | 담당 | 의존 관계 | 완료 기준 |
|---|---|---|---|
| 금액 근거 조사 | 읽기 전용 조사 담당 | 기존 청구·수강대장·특강 모델 | 정가 추정 없이 근거·권한 정의 |
| 서버 조회 | 서버 담당 | 조사·공유 타입 | 당월·반·명단 범위 읽기, 무자료·충돌 구분 |
| 출석·청구 UI | UI 담당 | 공유 타입; 서버와 파일 독립 | 금액 바로 표시, 실제 청구 창·실패 재시도 |
| 독립 QA·리뷰 | tester / reviewer | 구현 완료 | 실제 청구 모달·납부 폼, 정책·권한 경계 |
| 원본 SQL 통합·기록 | PM | 구현 완료 | 격리 PostgreSQL→실제 액션→실제 화면, 로컬 커밋 |

## 금액과 상태의 의미

- 한국시간 현재 월을 표시하며 `Payment.year/month`를 사용한다. 납기일로 청구 월을 추정하지 않는다.
- 해당 학생·반·월이 명시된 결제 원장의 금액·상태를 읽는다. 청구서가 없어도 결제 원장이 있으면 금액과 납부 여부를 표시한다.
- 청구 금액에는 셔틀비 등이 포함될 수 있어 ‘청구 금액’이라고 표시한다. 이를 순수 수강료로 단정하지 않는다.
- 결제 원장도 없으면 `CONFIRMED` 월 수강대장의 해당 반 기본액에서 할인·이월·일할 차감을 뺀 수강료를 보여준다. 학생 월 셔틀비는 각 반에 반복 가산하지 않는다.
- 확정 0원과 자료 없음은 다르다. 초안·자료 없음은 금액 미확인, 중복·반 미지정·상태/금액 충돌은 관리자 확인 필요로 표시한다.
- 월 수강대장 테이블이 없는 환경은 명시적으로 미설치로 구분한다. 설치된 테이블의 조회 장애를 빈 자료로 삼키지 않는다. 새 테이블·마이그레이션·활성화는 추가하지 않았다.
- 특강은 실제 출석 좌석→신청 항목을 연결한다. 전환 전 학생도 이름으로 추측하지 않으며 할인 후 **특강 전체 기간 수강료**를 월 수강료와 구분한다. 셔틀 포함 총청구액은 별도로 안내한다.

## 화면과 데이터 연결

- 출석 학생 행에 대상 월·금액·납부 상태와 ‘수강료·청구 확인’ 버튼을 추가했다.
- 금액 읽기는 출결 처리와 독립적이다. 지연·실패 중에도 출결 버튼을 사용할 수 있고 금액만 다시 조회한다.
- 학생별 청구 창은 실제 `ClassBillingSheet`, `BillingCard`, `PaymentRequestDialog`를 사용한다. 출석 진입에서는 선택 학생·당월·해당 반의 증명된 청구만 보여주고 전체 상태 필터로 시작한다.
- 청구서 없는 학생에게는 금액 근거·미발행 설명을 보여주며, 임의로 납부 확인 버튼을 만들지 않는다.
- 청구 창의 최신 요약을 해당 출석 행에만 반영한다. 납부 확인 요청 후에는 확인 대기로 표시하고 명단을 갱신한다. 확인 요청이 곧 납부 완료는 아니다.
- 새 읽기 액션은 세션 조회 권한과 실제 출석 명단을 확인한다. 클라이언트가 임의 학생 ID를 보내 다른 반의 금액을 조회할 수 없도록 서버에서 다시 제한한다.
- 기존 납부 확인 요청·관리자 승인 함수 본문은 변경하지 않았다. 조회만으로 청구 생성·발송·납부 상태 변경을 수행하지 않는다.

주요 변경 경로: `src/lib/staff-monthly-fee-{types,policy}.ts`, `src/lib/staff-monthly-fees.ts`, `src/app/actions/staff-billing.ts`, `SessionInProgressClient.tsx`, `ClassBillingSheet.tsx`, `StaffMonthlyFeeSummary.tsx`.

## 확인할 한계

- 당월 결제 원장과 확정 수강대장 모두 없으면 금액을 만들지 않고 관리자 확인으로 남긴다. 이 작업은 청구서 발행 기능이 아니다.
- 장부의 학생 월 셔틀비는 지정 청구 반의 배부 식별자가 없다. 차액만으로 해당 반 셔틀비라고 추정하지 않으므로 정상 합산 청구라도 근거가 충돌하면 확인 필요로 남을 수 있다.
- 청구서의 반 정보 불일치와 조회 도중 변경은 기존 관리자 승인 단계에서 최종 대조한다. 이번 읽기 검증을 전체 운영 DB 무결성 검증으로 해석하지 않는다.
- 운영 DB·Supabase 로그인·실제 현장 결제·외부 알림·배포는 실행하지 않았다. 인증/권한 제공자가 합성인 검사와 실제 운영 인증은 구분한다.
